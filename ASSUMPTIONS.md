# Assumptions

| ID | Assumption | Why I needed it | Impact if it is wrong |
|---|---|---|---|
| AS-01 | The five Home Essentials answers can be mapped to bands (for example, postal code → rating zone, versioned in Salesforce), so each country has a finite answer space that can be rated in a daily batch | A pre-computed grid keeps quotes available while the org is down (≈ 97%, `SALESFORCE_CONSTRAINTS.md:15`), and this is needed for the 99.5% target (C1) | Without a grid, quotes use live rating, quote availability is limited by the org (≈ 97%), and ADR-0002 declares the gap with C1 |
| AS-02 | The Salesforce platform team can compute the grid inside each org after the 05:00 UTC publication and expose it through the System API in a few bulk calls, with a Q1 effort that fits next to configuring the product in three orgs. To be confirmed in a December spike, with an answer before 15 Dec 2026 | If the cell builds the grid with one REST call per combination, the 40 req/s limit and the daily budget restrict it (`SALESFORCE_CONSTRAINTS.md:19,31,35`) | Plan B: the cell builds the grid over REST with at most 10,000 combinations per country (10,000 ÷ 10 req/s ≈ 17 min; 10,000 ÷ 250,000 = 4% of the MX channel budget). If the answer space is larger, live rating becomes the main path |
| AS-03 | The data that issuance needs (country-specific documents and consents, `SALESFORCE_CONSTRAINTS.md:8`) can be validated through the System API before payment while the org is up, so issuance failures after payment are rare | Purchase in the same session (BR-01) charges the customer before the policy is issued | More cases reach the manual exception queue (refund or manual issuance), and the 3-minute issuance target is missed more often |
| AS-04 | Purchases are spread over time like quotes, so the share of purchases made while an org is down is close to its unavailability (≈ 3%, `SALESFORCE_CONSTRAINTS.md:15`). The material has no purchase or issuance data | To set the initial target for policies issued and sent in ≤ 3 min (95%, `SLOS.md` §2) | We recalibrate the target after 30 days of measured data |
| AS-05 | The Q3 synthetic availability of the quote journey (`DELIVERY_METRICS.md:17`) is a valid starting baseline for the quote targets of the current products, until the BFF SLI has 30 days of data | To set interim targets that the cell can meet, instead of a 99.5% that the Salesforce availability already rules out (`SLOS.md` §2) | The synthetic values are higher than the org's ≈ 97% (`SALESFORCE_CONSTRAINTS.md:15`), so the BFF, which also counts timeouts, may measure less. In that case the first recalibration lowers the targets to the measured baseline |
| AS-06 | Legal accepts a documented basis for regional services that process the personal data of the three countries, if each country's data and secrets stay in separate stores and people can access only the countries they serve. The two approved Azure regions (`SCENARIO.md:25`) can hold the data of the three countries | ADR-0001 uses one regional deployment, and C5 asks for a documented basis | The components that process personal data (`channel-bff` and the quote Process API) move to one deployment per country (option B of ADR-0001). The code does not change |
| AS-07 | The MuleSoft deployment offers a persistent key-value store (Object Store) shared by the replicas of the Process API, with size and request-rate limits that fit the price grid and its daily load. We check it in the December spike, together with AS-02 | The grid must survive restarts and be readable by every replica (`ARCHITECTURE.md` §4), and the material does not say how MuleSoft is deployed (`SCENARIO.md:26`) | The grid moves to a small Azure Database for PostgreSQL owned by the Process API, a service already approved for the channel (`SCENARIO.md:25`). The Process API then needs network access to it, with a lookup p95 below 20 ms |
